Typed Tool Interfaces

The actuation boundary bridges stochastic neural deliberation and deterministic external software execution. While Tool Execution establishes the theoretical underpinnings of this boundary—formalizing hardware-style protection rings, typed Application Binary Interfaces (ABIs), capability-based access control, and mathematical idempotency—engineers implementing autonomous systems require practical, reusable specifications. This appendix serves as an engineering cheat sheet and reference guide for constructing robust, deterministic tool interfaces. It provides production-grade JSON Schema templates, formalizes grammar-constrained logit decoding mechanics at the GPU tensor layer, details distributed cryptographic nonce and capability lease implementations, and contrasts the token economics of deep execution primitives against shallow micro-tool architectures.

How to Use This Appendix

This appendix provides concrete implementation patterns and reference code for developers engineering tool boundaries. Reach for it when addressing specific failure modes in tool definitions, decoding pipelines, or execution gateways:

  • When tool calls fail validation due to schema hallucination or ambiguous typing: Use section 1.1 for strict schema rules, golden JSON/Pydantic templates, and anti-pattern checklists.
  • When models emit malformed JSON, unclosed brackets, or invalid enum variants: Use section 1.2 to implement grammar-constrained logit masking at the tensor layer.
  • When network timeouts, dropped connections, or model retries trigger duplicate side effects: Use section 1.3 for canonical argument hashing, trajectory nonces, and distributed lock workflows.
  • When subagents require bounded authority or sandboxed access controls: Use section 1.3 for cryptographic capability leases and monotonic attenuation patterns.
  • When static tool catalogs consume excessive KV-cache memory or degrade dispatch accuracy: Use section 1.4 to consolidate fragmented API wrappers into four canonical deep modules.

JSON Schema Best Practices for Tool Definitions

In an agentic architecture, tool schemas are not mere passive documentation; they represent the formal Interface Definition Language (IDL) compiled into model system prompts and grammar engines. A poorly specified schema causes attention dispersion, argument hallucination, and parsing exceptions. Production tool definitions must follow five core structural rules:

  1. Explicit property closure (additionalProperties: false): Neural models frequently invent plausible-sounding arguments (such as dry_run, verbose, or user_id) if the schema permits unconstrained properties. Restricting schemas with additionalProperties: false ensures the ABI boundary rejects undeclared inputs and allows finite automata compilers to bound decoding trees.
  2. Mandatory parameter arrays: Every required field must be explicitly listed in the top-level required array. Never rely on prose descriptions within parameter docstrings to convey that an argument is required.
  3. Restrictive type bounds and formatting: Use primitive types (string, integer, number, boolean, array, object) with explicit bounds. Constrain numbers with minimum and maximum, strings with pattern (regular expressions) or enum, and collections with minItems and maxItems.
  4. Semantically bounded descriptions with units: Parameter descriptions must declare units of measure (for example, timeout_ms rather than timeout), indexing conventions (such as 1-indexed line numbers), and expected nullability or default behavior.
  5. No ambiguous polymorphic unions: Avoid unconstrained anyOf or oneOf blocks lacking a discriminator tag. Autoregressive sampling degrades when navigating overlapping schemas without an explicit dispatch key.

Grammar-Constrained Logit Decoding

Even with strict JSON schemas, an autoregressive foundation model sampling tokens unconstrained from vocabulary \(V\) can emit syntactically invalid payloads (for example, unescaped newlines, trailing commas, or illegal property names). Classical systems handle these failures by catching JSON decode exceptions and injecting an error message back into the conversation context, asking the model to fix its mistake.

This post-hoc re-prompting approach imposes severe systems costs:

  1. Compounding Latency: Each corrective turn incurs a full round-trip through the inference engine, requiring prefill evaluation over thousands of context tokens.
  2. Context Fragmentation: Error traces and apology tokens clutter the prompt, displacing useful episodic memory and degrading attention focus.
  3. Stochastic Brittleness: A model that fails to produce valid JSON once has a non-negligible probability of failing again on the repair turn.

Grammar-constrained logit decoding eliminates syntax errors by enforcing structural invariants directly at the GPU tensor layer during generation (Willard and Louf 2023).

Willard, Brandon T., and Rémi Louf. 2023. “Efficient Guided Generation for Large Language Models.” arXiv Preprint arXiv:2307.09702.

The tensor masking mechanism

Let \(V\) denote the model’s vocabulary, with token indices \(v \in \{0, 1, \dots, |V|-1\}\). At generation step \(t\), the transformer backbone produces an unnormalized logit vector \(z_t \in \mathbb{R}^{|V|}\).

The tool schema is compiled ahead of time into a formal grammar represented as a Deterministic Finite Automaton (DFA) \(M = (Q, \Sigma, \delta, q_0, F)\), where:

  • \(Q\) is the finite set of parser states.
  • \(\Sigma\) is the alphabet of byte sequences.
  • \(\delta: Q \times \Sigma \to Q\) is the state transition function.
  • \(q_0 \in Q\) is the initial state.
  • \(F \subseteq Q\) is the set of accepting terminal states.

Let \(q_t \in Q\) represent the state of the automaton after consuming the token sequence emitted up to step \(t-1\). The set of legal next tokens \(\text{Valid}(q_t) \subseteq V\) comprises all tokens whose underlying byte sequence drives \(M\) into a valid non-error state:

\[\text{Valid}(q_t) = \big\{ v \in V \;\big|\; \delta^*(q_t, \text{bytes}(v)) \neq \emptyset \big\}\]

Before executing the softmax normalization kernel, the serving engine applies an elementwise binary mask to the logit vector:

\[\tilde{z}_{t, v} = \begin{cases} z_{t, v} & \text{if } v \in \text{Valid}(q_t) \\ -\infty & \text{if } v \notin \text{Valid}(q_t) \end{cases} \label{eq-vol3-app-b-masking}\]

When the normalized probability distribution is computed:

\[\mathbb{P}(y_t = v \mid x_{<t}) = \frac{\exp(\tilde{z}_{t, v})}{\sum_{j \in V} \exp(\tilde{z}_{t, j})}\]

the probability of every illegal token evaluates to exactly zero (\(\exp(-\infty) = 0\)). Consequently, the sampler cannot select a token that violates the schema grammar.

Performance and latency trade-off analysis

Grammar masking introduces a small per-token computational overhead during decoding, but it avoids multi-turn error correction loops. We quantify the trade-off by comparing trajectory latency under unconstrained decoding versus grammar-constrained decoding.

Let:

  • \(L_{\text{gen}}\) be the number of output tokens in a tool invocation (\(L_{\text{gen}} \approx 80\text{ tokens}\)).
  • \(t_{\text{decode}}\) be the per-token decoding latency (\(t_{\text{decode}} \approx 20\text{ ms}\)).
  • \(t_{\text{mask}}\) be the CUDA kernel overhead per token to evaluate the DFA bitmask (\(t_{\text{mask}} \approx 0.5\text{ ms}\)).
  • \(p_{\text{err}}\) be the unconstrained syntax error probability on the schema (\(p_{\text{err}} \in [0.03, 0.08]\) for frontier models).
  • \(T_{\text{repair}}\) be the latency penalty of a repair turn, including context prefill and regeneration (\(T_{\text{repair}} \approx 1{,}800\text{ ms}\)).

The expected latency of unconstrained generation with one corrective retry turn is:

\[\mathbb{E}[T_{\text{unconstrained}}] = L_{\text{gen}} \cdot t_{\text{decode}} + p_{\text{err}} \cdot T_{\text{repair}}\]

The expected latency of grammar-constrained decoding is deterministic:

\[T_{\text{constrained}} = L_{\text{gen}} \cdot (t_{\text{decode}} + t_{\text{mask}})\]

Equating the two expressions yields the breakeven error rate \(p_{\text{break}}\):

\[L_{\text{gen}} \cdot t_{\text{decode}} + p_{\text{break}} \cdot T_{\text{repair}} = L_{\text{gen}} \cdot t_{\text{decode}} + L_{\text{gen}} \cdot t_{\text{mask}}\]

\[p_{\text{break}} = \frac{L_{\text{gen}} \cdot t_{\text{mask}}}{T_{\text{repair}}} = \frac{80 \times 0.5\text{ ms}}{1{,}800\text{ ms}} = \frac{40\text{ ms}}{1{,}800\text{ ms}} \approx 2.22\%\]

Whenever the unconstrained syntax failure rate exceeds \(2.22\%\), grammar-constrained decoding delivers lower wall-clock latency in addition to guaranteeing zero schema exceptions.

Tool Idempotency and Capability Leases

In distributed environments, tool invocations cross network boundaries, microVM sandboxes, and remote database connections. Network timeouts, worker crashes, or agent deliberation loops can trigger retries of previously initiated actions. Without explicit system guarantees, these retries cause unintended duplicate mutations (for example, charging a credit card twice or creating duplicate database records).

To ensure safe execution, tool boundaries must enforce two operational guarantees:

  1. Mathematical Idempotency: Repeated execution of an identical mutating action yields the same state as a single execution (\(f(f(s)) = f(s)\)).
  2. Capability Leases: Every action must be authorized by an explicit, unforgeable, and temporally bounded capability token, abolishing ambient authority (Saltzer and Schroeder 1975; Dennis and Van Horn 1966).
Saltzer, J. H., and M. D. Schroeder. 1975. “The Protection of Information in Computer Systems.” Proceedings of the IEEE 63 (9): 1278–308. https://doi.org/10.1109/proc.1975.9939.

The distributed idempotency pipeline

As established in Tool Execution, guaranteeing idempotency across stochastic control loops requires binding every mutating tool invocation to a deterministic Trajectory Nonce \(\eta\):

\[\eta = \text{HMAC-SHA256}\Big(K_{\text{secret}}, \text{trajectory\_id} \mathbin{\Vert} \text{step\_idx} \mathbin{\Vert} \text{tool\_name} \mathbin{\Vert} \text{CanonicalJSON}(\text{arguments})\Big)\]

Standard JSON serialization is non-deterministic because dictionary key ordering varies across runtimes. If an agent emits {"path": "/a", "force": true} on its initial call and {"force": true, "path": "/a"} on a retry, naive string hashing yields different nonces, defeating deduplication. Arguments must be normalized using canonical JSON serialization (RFC 8785), which lexicographically sorts all keys and standardizes whitespace.

When an invocation carrying nonce \(\eta\) reaches the execution gateway, the runtime coordinates execution through an atomic distributed state store (such as Redis or DynamoDB) using a three-stage lifecycle:

  1. Atomic Lock Acquisition: The gateway attempts to acquire an in-flight lock:

    SET idempotency:η "IN_FLIGHT" NX PX 30000

    If the key already exists with status IN_FLIGHT, a concurrent worker is processing the mutation; the gateway waits or returns a retry backoff response.

  2. Completed Execution Replay: If the key exists with status COMPLETED, the gateway bypasses tool execution entirely and returns the cached observation payload.

  3. Execution and Commit: If the lock is successfully acquired (NX succeeded), the gateway dispatches the tool to the sandbox. Upon completion, it updates the state key to COMPLETED with an expiration time-to-live (TTL) and records the serialized observation.

Capability leases and monotonic attenuation

Ambient authority—where any authenticated component inherits all permissions of the system—is a critical vulnerability in agentic architectures. If an untrusted web-browsing agent parses a prompt-injected document, it must not possess ambient credentials to execute shell commands or read private files.

Under the Dennis and Van Horn capability model (Dennis and Van Horn 1966), an agent can execute an action only by presenting an explicit Capability Lease:

Dennis, Jack B., and Earl C. Van Horn. 1966. “Programming Semantics for Multiprogrammed Computations.” Communications of the ACM 9 (3): 143–55. https://doi.org/10.1145/365230.365252.

\[\mathcal{K} = \big(\text{CID}, \mathcal{R}, \mathcal{O}, t_{\text{exp}}, \mathcal{Q}, \sigma\big)\]

where:

  • \(\text{CID} \in \{0, 1\}^{256}\) is a unique cryptographic capability identifier.
  • \(\mathcal{R}\) is the authorized resource scope (for example, /workspace/repo/**).
  • \(\mathcal{O}\) is the set of permitted operations (for example, {"read", "edit"}).
  • \(t_{\text{exp}}\) is the epoch timestamp marking lease expiration.
  • \(\mathcal{Q}\) is the allocated token and financial expenditure quota.
  • \(\sigma = \text{Sign}_{K_{\text{kernel}}}(\text{CID} \mathbin{\Vert} \mathcal{R} \mathbin{\Vert} \mathcal{O} \mathbin{\Vert} t_{\text{exp}} \mathbin{\Vert} \mathcal{Q})\) is the cryptographic signature.

When a root agent delegates subtasks to child subagents, capability leases must attenuate monotonically:

\[\mathcal{K}_{\text{child}} \subseteq \mathcal{K}_{\text{parent}}\]

A child cannot be granted a resource scope wider than its parent, an operation the parent lacks, a longer expiration time, or a larger compute quota.

Deep Modules vs. Shallow Micro-Tools

When integrating agents with enterprise infrastructure, a common design instinct is to mirror existing REST APIs by registering one tool per endpoint (for example, git_status, git_diff, git_add, git_commit, git_push, k8s_get_pods, k8s_describe_pod, k8s_delete_pod). This produces a catalog of dozens or hundreds of shallow micro-tools.

In A Philosophy of Software Design, John Ousterhout defines a shallow module as one whose interface surface area is large relative to the functionality it provides (Ousterhout 2018). For autonomous agents, shallow interfaces impose a dual tax: they consume substantial prompt context bandwidth and disperse attention during tool selection. In contrast, deep modules present simple, compact interfaces that encapsulate expressive execution power within a sandboxed runtime.

Ousterhout, John. 2018. A Philosophy of Software Design. Yaknyam Press.

The prompt token tax and attention dispersion

To expose a tool to a model, its complete JSON Schema must be serialized into the system prompt context. Let \(K\) denote the number of tools registered in the active catalog, and let \(S_i\) be the token length of tool schema \(i\). Across an autonomous deliberation trajectory spanning \(N\) execution steps, the cumulative prefill token spend \(T_{\text{prefill}}\) consumed purely by re-ingesting tool definitions is:

\[T_{\text{prefill}} = N \sum_{i=1}^K S_i\]

Consider an agent operating with a shallow catalog of \(K = 80\) tools, where each schema averages \(S = 350\text{ tokens}\). The catalog consumes \(28{,}000\text{ tokens}\) on every step. Over a 40-step trajectory, the model evaluates:

\[40 \times 28{,}000 = 1{,}120{,}000\text{ prefill tokens}\]

just to read tool descriptions. In contrast, an agent using \(K = 4\) deep modules, each averaging \(S = 250\text{ tokens}\) (\(1{,}000\text{ tokens/step}\)), consumes:

\[40 \times 1{,}000 = 40{,}000\text{ prefill tokens}\]

Consolidating into deep modules eliminates \(1{,}080{,}000\) prefill tokens—a \(96.4\%\) reduction.

Beyond compute costs, shallow catalogs degrade reasoning quality. When \(K\) exceeds 30, the model’s cross-attention weights over tool schemas flatten. In benchmark evaluations, tool selection error rates rise from under \(2\%\) when selecting among 4 deep modules to over \(18\%\) when selecting among 80 shallow endpoints. The model frequently hallucinates arguments across similar tools (for example, passing git_diff flags to git_status).

The four canonical deep tool modules

Frontier software engineering agents converge on four canonical deep execution primitives. Rather than wrapping individual shell commands or file operations into dozens of micro-tools, the runtime exposes four robust interfaces:

  1. BashExecute: A stateful POSIX shell execution primitive inside a sandboxed microVM. It handles compilers, test runners, git version control, package managers, and directory navigation.
  2. FileView: A windowed file inspection primitive that requires explicit line offset and count parameters, preventing accidental context dumps of multi-megabyte files.
  3. FileEdit: An atomic string replacement primitive enforcing unique matching invariants, preventing accidental partial edits or file corruption.
  4. GrepSearch: A high-performance regular expression search primitive that scans repositories and returns structured file and line matches without shell quoting hazards.

Listing 5 details the schema specifications for these four deep modules.

By adopting deep modules, agent architectures preserve prompt token bandwidth, minimize KV-cache allocation in accelerator memory, eliminate tool selection hallucinations, and unify security sandboxing within an isolated execution supervisor.
