Results, Provenance, and Packaging

A benchmark that cannot be reviewed is a demo. MLPerf EDU treats the artifacts of a run as first-class products, designed to be handed to an instructor, an artifact evaluation committee, or a co-author.

First Result Walkthrough

Begin with the lead card, then move from execution evidence to claim evidence. The first five checks prevent a fast number or green setup state from being mistaken for a valid benchmark conclusion.

Check What to Find What It Means
Execution Completed or failed paths Whether the runner produced an evaluable result
Quality Observed metric, direction, target, and pass or miss Whether the declared quality contract was evaluated and met
Configuration Workload, profile, mode, phase, device, seed, and controlled settings Which experiment the result actually represents
Lineage Dataset revision, model source, training checkpoint, and inference dependency Which inputs produced the observation
Provenance Manifest state, hashes, and run fingerprint Whether the recorded artifacts still match their manifest

A min report normally stops after functional execution and provenance. A quality-bearing max or pro report can continue through target evaluation. A target miss may still be a valid result. An execution failure or invalid manifest cannot support a quality conclusion.

The evidence states form a claim ladder.

executed → provenance verified → quality evaluated → target met or missed
         → comparison eligible → repeatability established → publication eligible

The current milestone accepts one complete run for initial quality evaluation. It does not skip the later repeatability, independent reproduction, and release review needed for a publication claim.

The Four Artifacts

Every workload run emits four files, named after the workload and profile:

Artifact Role
*_report.json The complete result with metrics, environment fingerprint, asset dossiers, and quality status
*_report.html The default dashboard with the lead result, target decision, configuration, lineage, and provenance
*_report.csv Flat metrics for spreadsheets and plotting
*.provd.json The provenance artifact: SHA-256 hashes of model state and assets

The .provd.json artifact binds a result to its recorded inputs and environment. For training workloads it can capture the frozen model state_dict hash. Inference workloads can declare and verify a shared checkpoint dependency. Verification proves that the recorded files match the manifest; it does not by itself establish benchmark validity or MLCommons acceptance.

Reading the Dashboard

The lead view is derived from the report rather than a fixed profile layout. A functional-only report shows a readiness meter, passed or failed paths, and clearly secondary diagnostic values. A quality-bearing report shows target decisions and a direction-aware attainment bar where 100% means the declared gate. A mixed report keeps separate readiness and quality meters so setup success cannot hide a missed quality target.

Raw benchmark values are not combined into one cross-workload chart. Accuracy, FID, loss, AUC, and pass@1 use different units and improve in different directions. The normalized target-attainment view supports valid comparison without implying that the raw metrics share a scale. Distribution charts belong to the later stability view and appear only when repeated run evidence exists.

The remaining sections preserve the context needed to interpret each result. Run Configuration records the exact mode, phase, backend, device, seed, and workload settings. Model Lineage distinguishes a locally trained checkpoint from an upstream pretrained checkpoint and follows it through inference and evaluation. Provenance links the JSON report, manifest, run fingerprint, and checkpoint digest.

The suite health report is a second, intentionally smaller view. mlperf health runs every registered min path, verifies the manifests, and groups functional results by suite. It never places a min diagnostic beside a max quality target. Instead, each row says that quality was not evaluated and links to the detailed run artifacts.

A pro experiment-plan report adds the research question, hypothesis, declared variables, controls, exact plan hash, and a condition matrix. Each condition keeps its own quality card. The shared visualization boundary is normalized target attainment, where 100% means that condition reached its declared gate. Unrelated raw metrics never share an axis. The CSV carries the plan ID, condition name, plan hash, planned device, outer-run count, and declared environment settings for notebook analysis. When a plan labels one condition baseline and another candidate, the dashboard can show a descriptive throughput delta. That bar explains the observed one-run result; it does not bypass the standard compatibility gate or claim a stable distribution. An imported instructor baseline is labeled as imported in HTML and CSV. Its wrapper manifest binds the unchanged source report and source manifest, and its original run fingerprint remains the comparison boundary.

The aggregate provenance manifest binds the exact source plan, aggregate JSON, and every nonfailed child manifest. A missing or invalid child manifest blocks the delta and downgrades the condition to an execution failure.

Reading and Converting Reports

uv run mlperf report submissions/image-max --format summary
uv run mlperf report submissions/causal-language-modeling_training_max_report.json
uv run mlperf report submissions/causal-language-modeling_training_max_report.json --format html --open
uv run mlperf report submissions/current/image-classification_max_report.json \
  --baseline submissions/baseline/image-classification_max_report.json \
  --format html --open
uv run mlperf report submissions/causal-language-modeling_training_max_report.json --format csv
uv run mlperf report submissions --format html --open                    # latest in a directory

Pointing report at a directory picks up the most recent run, which avoids copying timestamped filenames. Use a specific JSON path when a directory contains several results and the exact selection matters. HTML generation does not open a browser unless --open is present.

An explicit --baseline adds a comparison section to JSON and HTML output. The dashboard labels structurally compatible results as exploratory until both source manifests verify. Quality values are compared only when the workload, profile, mode, phase, dataset, evaluator, and target contract match. Performance bars and improvement percentages require the same checkpoint lineage and complete comparison fingerprint as well. The dashboard lists the mismatched boundary when a comparison is invalid. See the result comparison example for a compatible rerun and an intentionally blocked batch-size change.

Verifying and Packaging a Submission

uv run mlperf verify submissions/causal-language-modeling_training_max.provd.json
uv run mlperf package \
  submissions/05-assignment/image-classification_min.provd.json \
  --output submissions/05-assignment.zip

verify re-checks the provenance manifest, including its hashes and recorded quality status. package bundles a verified, portable result for grading or artifact review. Many score-bearing max results bind fetch-only or release-review dataset bytes and are intentionally refused. Example 05 uses the dataset-free image-classification min path to teach portable packaging without making a quality claim. Release CI checks verification again after clean extraction.

What the Fingerprint Buys You

Reports embed the hardware and software fingerprint of the machine that produced them, including Python, PyTorch, platform, and accelerator details. Matching profiles and disclosed fingerprints are necessary for comparison, but they are not sufficient. The workload, mode, phase, quality result, dataset recipe, checkpoint lineage, and release-validation state must also match.

The fingerprint distinguishes an availability-detected backend from the report-selected backend that executed the workload. Its comparison digest binds CPU topology, accelerator runtime and driver metadata when discoverable, PyTorch threading and numeric policies, deterministic and benchmark flags, and an explicit allowlist of performance-related environment settings. If a report declares precision or compilation mode, the run comparison digest binds those selections as well.
